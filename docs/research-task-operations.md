## 本次试验

仅使用 `/private/tmp/creative-iteration0-probe` 中的隔离客户端和本机接收器。随机测试凭据写入权限 0600 的私有文件，没有模型密钥、真实候选或用户信息。提示词只引用脚本路径，不包含凭据。接收器设置 8 分钟自动退出；计划用短周期独立唤起触发恢复和重叠场景。

接收器先对首份载荷入库后断开连接，后续按同一请求体 SHA-256 返回原回执；这是为迭代 0 准备的运输层替身，尚不实现完整 v1 Schema/资格校验。实测接收计数为 0，无有效 run_id/ordinal，未产生可确认批次。故不以脚本存在或手动运行作为定时闭环证据。

平台报告网络权限失败后删除了 `creative-0`；未扩大后台权限、未启用真实搜寻、未替换成独立 Go 程序。公开仓库只保留本记录，不提交测试凭据、私有 outbox 或任务运行的完整上下文。

## 下一次接入验证的条件

在明确授权且网络/工具权限适配的执行环境，重新建立隔离接收器和临时任务，逐项验证后清理任务：

1. 定时任务实际读取任务、以绑定凭据发送 HTTP；凭据只能用于指定 Creative API 地址。
2. 第一次独立运行保存准确请求字节和稳定 batch_id，模拟服务器已接收但响应丢失。
3. 第二次独立运行从工件恢复，不改字节/ID，查询或重试获得相同回执，只入库一次。
4. 前轮持续运行时再次定时触发，确认平台跳过或排队。提示词写“不要重叠”不算实现，也不以人工锁代替平台证据。
5. 验证网络故障、工件不完整、取消/达标/规则变更的恢复边界；真实三接口联调归迭代 4。
